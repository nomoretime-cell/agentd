## 核心洞察

Anthropic 发布的工程实践指南系统拆解了**有状态、主动式（Proactive）、无人值守 Agent** 的底层系统架构。

文章最核心的架构共识在于：**“全天候在线（Always-on）”只是一种用户体验假象，而非底层进程持续运行。** 实际上，Agent 绝大部分时间处于休眠状态（零 Token 消耗），仅在外部事件或自设定时器触发时短暂唤醒，执行一次离散的 **Run（单次运行）**，在 **Session（会话上下文，记录消息与工具调用轨迹）** 中完成处理并持久化状态后，立即释放资源回到休眠。

这一架构近期得以大规模落地主要依赖两大演进：
1. **模型判断力跃升**：最新模型在意图理解以及“何时主动汇报、何时保持静默”的边界判断上显著成熟。
2. **长程任务推理成本骤降**：以长程编码基准测试为例，Opus 5.5 解决单任务的成本比 Opus 5 降低了 **78%**（常规工作负载降幅达 **40%**）。

## 整体运行闭环架构

全天候 Agent 的内核依然是标准的 Agent Loop，真正的架构差异在于外围控制“何时唤醒、跨次运行保留什么、结果如何安全触达用户”的**五大核心原语（Primitives）**：

~~~text
  [外部 Webhook / 用户消息]               [Timers 定时器表]
             │                                  │ (Scheduler 轮询到期项)
             ▼                                  ▼
      (HTTP Handler) ────────────────► [ 1. Event Inbox 事件收件箱 ]
       快速 ACK 去重写入                         │ (单 Inbox 严格限 1 个活跃 Worker)
                                                ▼
                                         (Worker 唤醒拉取)
                                                │
       ┌────────────────────────────────────────┴────────────────────────────────────────┐
       ▼                                        ▼                                        ▼
[ 3. Memory 记忆存储 ]                 [ Agent 核心执行循环 ]                   [ 4. Permissions 权限层 ]
• instructions.md (必加载)            • 恢复已有 Session 或开启新 Session      • 外部网关代理注入凭证 (隔离密钥)
• 用户笔记 (索引 + 按需加载详情)       • Prompt Caching 降低固定前缀开销        • Auto Mode 分类器实时拦截高危操作
• 任务进度 & 已发消息防重              • 更新记忆 / 按需设定下一次 Timer        • Deferred Tool Calls 挂起等待审批
       └────────────────────────────────────────┬────────────────────────────────────────┘
                                                │
                       ┌────────────────────────┼────────────────────────┐
                       ▼                        ▼                        ▼
                 [静默结束 Run]         [挂起并保存半截状态]      [ 5. Outbox 发件箱表 ]
                 (判定无需打扰)         (释放 Worker；用户批复            │
                                        后作为新事件回流 Inbox)           ▼
                                                                   (Dispatcher) ──► 触达用户
~~~

## 五大核心原语速查表

| 核心原语 | 核心职责 | 关键工程模式 |
| :--- | :--- | :--- |
| **1. Event Inbox（事件收件箱）** | 持久化缓冲与并发互斥 | 严禁事件源直连 Agent Loop；HTTP Handler 极速 ACK 写入关系表并按源 ID 去重；强制**单 Inbox 最多 1 个活跃 Worker** 防止竞态；合并连续短消息（Batching）；重度安全扫描推迟到 Run 内执行。 |
| **2. Timers（定时器）** | 自驱跟进与周期主动性 | 与 Inbox 物理分表，确保 Inbox 仅存待执行项；拆分为 **Follow-ups**（Agent 自设单次跟进）与 **Schedules**（Cron 周期任务）；后台 Scheduler 扫描到期项并转化为标准事件推入 Inbox。 |
| **3. Memory（记忆系统）** | 跨临时 Worker 的状态连续性 | 将数据库或对象存储映射为**虚拟文件目录**；仅存储外部系统无法重新查到的信息（外部系统数据只存 ID/指针）；采用**“常驻索引 + 按需加载详情文件”**配合 Prompt Caching 控制前缀开销；支持离线 **Dreaming** 整理。 |
| **4. Permissions（权限与安全）** | 无人值守防线与非阻塞审批 | 三层机制：**外部凭证代理**（密钥绝不进上下文）、**Auto Mode 实时分类器**（拦截高危调用）、**延迟工具调用（Deferred Tool Calls）**（遇人工审批即序列化保存半截状态并退出释放 Worker，批复结果从 Inbox 回流恢复）。 |
| **5. Outbox（发件箱）** | 触达节奏、重试与降噪 | 不向用户流式暴露思考链与工具轨迹；Run 仅以“静默退出 / 挂起等待审批 / 写入精简结果”收尾；独立 Outbox 表与 Dispatcher 实现速率控制与失败重试；遵循**初期保持安静、逐步赢得信任**原则。 |

## 五大核心架构原语详解

### 1. 事件收件箱（Event Inbox）：持久化缓冲与并发控制

全天候 Agent 会同时面对用户消息、第三方 Webhook、后台定时器等多种触发源。如果让事件源直接调用 Agent 运行时，并发到达的事件会引发竞态覆盖，而进程崩溃则会直接导致事件丢失。

- **三段式解耦结构**：持久化的事件表（推荐关系型数据库，按事件源唯一 ID 去重，初期建议采用**单用户单 Inbox** 隔离模型） + 负责接收写入的 HTTP Handler + 后台拉取执行的 Worker。
- **快响应、慢校验**：HTTP Handler 必须极速返回 ACK（防止外部 Webhook 超时重复推送），仅执行签名等轻量校验；诸如 **Prompt 注入检测**等高耗时安全检查，一律推迟到 Worker 启动后的 Run 内部执行。
- **单 Worker 互斥锁**：同一个 Inbox 在同一时刻**严格只允许一个活跃 Worker**，从根本上消除重复执行与记忆互相覆盖。
- **消息合并（Batching）**：当用户在短时间内连续发送多条碎片消息时，Worker 拉取时将其打包进同一次 Run，由 Agent 一次性完整回复。
- **故障自愈**：Inbox 表是唯一事实来源（Source of Truth）。Worker 唤醒后先读表，若运行中途发生容器崩溃，新拉起的 Worker 可直接读取未标记完成的事件安全重试。

### 2. 定时器（Timers）：赋予 Agent 主动性

定时器与 Event Inbox 分离存储，确保 Inbox 中永远只有“当下立即可执行”的工作项。定时器主要分为两类：

- **跟进提醒（Follow-ups）**：Agent 在执行过程中为自己设定的单次截止时间（例如：“邮件已发出，若 24 小时内未收到客户回复，明天此时唤醒我进行跟进”）。
- **周期计划（Schedules）**：固定频率触发的常规例行任务（如每日晨报、每周巡检），表结构需额外维护周期调度规则。
- **统一触发路径**：定时器本身不直接启动 Agent Loop，而是由后台 Scheduler（自建轮询服务或持久化执行引擎）定期扫描到期记录——将 Follow-up 标记为已完成、将 Schedule 推进至下一触发周期，随后向 **Event Inbox** 插入一条标准事件，复用统一的 Worker 唤醒链路。

### 3. 记忆系统（Memory）：跨运行周期的连续性

由于后台 Worker 是无状态且随时可能销毁重建的，记忆层必须映射到底层持久化存储（数据库或对象存储）支撑的**虚拟文件目录**上。核心设计原则是：**只存储无法从外部系统重新查询到的信息**（例如任务详情若已在 Issue Tracker 中，记忆里仅保留对应的 Issue ID 或指针）。

- **四类标准记忆文件**：
  1. **用户指令（User instructions）**：用户对 Agent 行为规范的长期要求，每次 Run 启动时全量加载。
  2. **用户笔记（User notes）**：用户的角色背景、偏好习惯及历史纠错记录。随体量增长拆分为多个细粒度文件，**每次 Run 启动仅加载索引（Index）**，需要具体细节时再由 Agent 按需读取对应文件。
  3. **历史已发消息（Past messages）**：记录已向用户主动汇报过的内容摘要，避免跨 Run 重复发送雷同通知。
  4. **任务进度（Task progress）**：每个长线任务维护独立的进度文件（记录已完成步骤与待办事项），同样采用**“启动加载索引 + 按需读取详情”**模式，支撑跨周期断点续做。
- **Dreaming（离线整理机制）**：除了 Run 执行期间的实时读写外，可引入异步后台整理进程回顾历史 Session，剔除过期的事实记忆，并提炼跨多次运行才显现的行为模式。
- **上下文窗口与成本控制**：System Prompt、工具定义与基础常驻记忆构成了每次 Run 的固定前缀开销。需保持前缀精简并充分结合 **Prompt Caching**。

### 4. 权限与安全（Permissions）：无人值守的风险防线

Agent 持有用户授权并在后台自主运行，架构上必须在“自动化效率”与“安全边界”之间构建三道防线：

- **外部凭证代理（Credential Proxy）**：密码、API Key、OAuth Token 等敏感凭据绝不进入 Agent 的上下文窗口或沙箱运行环境。Agent 仅发出不含凭据的请求，由运行环境外部的安全代理网关拦截、校验并注入真实凭据后再向外转发。
- **自动模式（Auto Mode）**：引入实时分类器（Classifiers）审查工具调用动作，自动拦截高风险操作并向模型返回阻断反馈，迫使模型寻找更安全的替代路径。
- **非阻塞的延迟工具调用（Deferred Tool Calls）**：当遇到必须由人类审批或补充信息的关键操作时，绝不能让 Worker 进程原地阻塞干等。系统通过 Hook 挂起当前工具调用，**立即结束本次 Run 并将执行到一半的 Session 状态完整序列化保存**，释放 Worker 去处理其他事件。同时向前端（例如通过 MCP Apps 渲染交互式审批卡片）推送请求；待用户点击确认后，审批结果作为一条标准新事件写回 Event Inbox，唤醒新 Run 无缝恢复此前挂起的工具调用现场。

### 5. 发件箱（Outbox）：触达节奏与降噪控制

与传统对话式 Agent 实时流式输出思考链（CoT）和工具调用过程不同，全天候 Agent 在后台静默运行，每次 Run 结束只有三种确定出口：**向 Outbox 写入精简结论**、**判定无需打扰直接静默退出**、或**触发 Deferred Tool Call 请求人工介入**。

- **执行与投递解耦**：轻量场景可直接暴露 `send` 工具；当涉及多渠道频率控制（Rate-limiting / Pacing）或网络异常重试时，应建立独立的 Outbox 表与后台 Dispatcher 服务，将“任务推理完成”与“消息实际触达”彻底解耦。
- **克制打扰与阈值校准**：推送过多会迅速退化为噪音导致用户关闭通知，推送过少则会遗漏关键节点。工程上应专门构建离线 Evals 来校准通知触发阈值，并在产品上线初期坚持**“宁可少发、保持安静，随时间推移逐步赢得用户信任与注意力”**的演进策略。

## 关键工程权衡与实现细节

1. **运行期新事件冲突（Mid-run Event Collisions）**  
   由于单 Inbox 限制最多一个活跃 Worker，当某次 Run 正在执行时若又有新事件写入 Inbox，架构上必须明确定义冲突处理策略：
   - 保守排队：留待当前 Run 结束后立即开启下一次 Run 处理（最简单稳健）；
   - 动态折叠：在当前 Agent Loop 的下一个 Step 动态拉取并注入新事件；
   - 抢占重启：中断当前未完成的 Run 并回滚或合并重启。
2. **会话压缩与轮转（Session Compaction vs. Rollover）**  
   恢复已有 Session 需要重新加载历史消息与工具调用记录。当单 Session 上下文膨胀到逼近上限时，无论是执行上下文摘要压缩（Compaction）还是开启全新 Session，都会不可避免地丢失底层工具交互细节——因此必须要求 Agent **在运行过程中将关键进展增量落盘到 `task_progress` 记忆文件**，而非等到上下文截断时才补救。
3. **同步阻塞转纯事件驱动**  
   将人工审批（Human-in-the-loop）从传统的“长连接/协程挂起等待”改造为“状态快照落盘 + Inbox 事件回流唤醒”，本质上是将有状态的同步长事务拆解成了无状态 Worker 上的纯事件驱动状态机，大幅提升了系统的水平扩展能力与容错性。
